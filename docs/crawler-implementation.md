# Crawler Implementation Notes

Status: implemented baseline; these notes also record the retained operational invariants.

These notes convert the current Nettiauto source research into the first crawler
design. The crawler should stay HTTP-first and should not use browser automation
unless the source behavior changes enough to require it.

## Source Queries

The first implementation should seed two Nettiauto passenger-car Source Search
Queries:

| Crawl kind | Path | Search hash |
| --- | --- | --- |
| current | `/vaihtoautot` | `P2236304442` |
| sold | `/hakutulokset` | `P82984997` |

The `haku=P...` value should be treated as an opaque Source Search Query hash.
It appears to be generated by Nettiauto's search/save-search flow, not by a
client-side algorithm that we should reproduce.

## Cadence Scheduling

Graphile Worker owns the recurring scheduler wakeup through
`apps/worker/crontab`. The crontab runs `schedule_nettiauto_crawl` once per day
in UTC. That task does not blindly crawl every day; it reads
`source_search_queries.target_cadence_interval` and only enqueues due Source
Search Queries. Cadence is measured from the latest successful, partial, or
failed crawl attempt so conservative `CRAWLER_MAX_PAGES_PER_RUN` settings do
not cause automatic daily recrawls.

Default cadence:

| Crawl kind | Cadence |
| --- | --- |
| current | 7 days |
| sold | 30 days |

The Admin Panel's manual crawl action enqueues `schedule_nettiauto_crawl` with
`force: true`, which bypasses cadence but still skips Source Search Queries
that already have an active Crawl Run.

`CRAWLER_MAX_PAGES_PER_RUN` controls the per-query page cap. A positive value
fetches at most that many Search Result Pages. `0` means no configured cap; the
crawler still stops at the Source-reported `total_page` from the AJAX response.
Do not crawl until an empty page is seen, because Nettiauto may return
non-empty JSON for page numbers beyond `total_page`.

## Fetch Strategy

Use the same endpoint URLs for page 1 and later pages:

```text
https://www.nettiauto.com/vaihtoautot?haku=P2236304442&page=1
https://www.nettiauto.com/hakutulokset?haku=P82984997&page=1
```

Send an AJAX-style request:

```text
Accept: */*
X-Requested-With: XMLHttpRequest
Referer: https://www.nettiauto.com/<path>?haku=<hash>
```

The live research showed that `X-Requested-With: XMLHttpRequest` is the
important difference between document HTML and JSON. `Accept: application/json`
alone did not force JSON.

Do not send browser session cookies by default. Do not store cookies or
Cloudflare clearance values in the database or logs.

Expected JSON response keys:

```text
total_ads
ad_listing_data
pagination_small_view
pagination_large_view
quick_filter_option
current_page
total_page
```

Treat a redirect, HTML document, Cloudflare challenge, 429, 403, or unknown body
shape as a fetch-level failure or block signal, not as a parser failure.

## Job Shape

Use Graphile Worker tasks instead of a raw loop.

Deployed task split:

```text
schedule_nettiauto_crawl
  creates Crawl Run rows for due Source Search Queries
  enqueues the first crawl_nettiauto_search_page job

crawl_nettiauto_search_page
  fetches and persists one Search Result Page
  completes the Crawl Run or schedules the next page
  optionally schedules capped, lower-priority detail work

crawl_nettiauto_detail_page
  best-effort Detail Page Data enrichment
  never determines authoritative Crawl Run completion

NettiautoCrawlExecution
  owns orchestration, evidence ordering, retries, pauses, and completion policy
```

The legacy `crawl_nettiauto_search_query` and `finalize_nettiauto_crawl_run`
handlers remain only for already-queued deployment compatibility. Remove them
after confirming the production Graphile queue has drained.

## Parser Strategy

The primary parser should consume AJAX JSON and parse `ad_listing_data`.

Use a real HTML parser for implementation. Regex is acceptable for short-lived
research probes, but production parsing should use a structured parser such as
Cheerio, parse5, or another deliberately chosen package.

For each listing card:

1. Locate card-level `data-datalayer`.
2. Parse it as Source payload JSON.
3. Extract `item_id` as Source Listing ID.
4. Extract source URL from the listing link when present.
5. Keep the listing-card HTML fragment as Raw Listing Data.
6. Extract image URLs from `picture`, `source`, and `img` elements.
7. Validate the parsed payload with Zod before normalization.

Expected `data-datalayer` fields from Search Result Data:

```text
item_id
item_name
item_brand
item_variant
item_seller
item_year_model
item_vehicle_price
item_mileage
item_power_type
item_ad_status
item_list_id
item_list_name
item_list_location
position
page_number
```

The parser should tolerate missing optional fields but fail loudly when identity
is missing. A card without `item_id` should not produce a Listing.

## Current vs Sold

Current and sold crawls are separate Crawl Runs with separate Source Search
Queries.

Expected labels:

```text
current endpoint: item_ad_status = Myynnissä
sold endpoint:    item_ad_status = Myyty
```

Normalize availability this way:

```text
sold crawl with Myyty label       -> sold
current crawl with Myynnissä label -> active
otherwise                         -> unknown, with source label retained
```

The implementation should compare Source Labels using Unicode normalization but
retain the original Source Label. Do not infer sold status from absence in a
Current Listings Crawl.

Fast-lane `Ohituskaista` cards are still real Listings and should be ingested.
Keep `item_list_id`, `position`, and `page_number` so analytics can later filter
or audit promoted placements.

## Raw Data Policy

For each Search Result Page, store:

- fetch metadata in `source_fetches`;
- one `raw_listing_records` row per listing card;
- the `data-datalayer` object as `source_payload`;
- the listing-card HTML fragment as `source_html_fragment`;
- parser version and payload hash.

Do not store the full fetched HTML document or full AJAX response as product
data by default. A local development fetch cache can store complete responses to
avoid repeatedly hitting Nettiauto while building parsers.

## Idempotent Persistence

The page writer should be retry-safe:

- Upsert `listings` on `(source, source_listing_id)`.
- Insert or upsert `raw_listing_records` on
  `(source_fetch_id, source_listing_id, record_kind)`.
- Insert or upsert `listing_sightings` for the crawl/page/listing.
- Insert `listing_snapshots` only when the Listing's normalized `change_hash`
  is new.
- Upsert `listing_images` on `(listing_id, image_url)`.

The writer should use one transaction per fetched page. A retry after a crash
must not double-count sightings or create duplicate snapshots.

## Crawl Politeness

Start conservatively:

- require an explicit crawler enable switch before making live Source requests;
- one Nettiauto fetch at a time;
- delay between page fetches;
- no browser automation on the default transport;
- no login/session scraping;
- no credentialed sessions, CAPTCHA solving, or automatic fallback chain;
- stop or back off on 403, 429, challenge pages, repeated redirects, or unusual
  body shapes;
- keep Current Listings Crawl fresher than Sold Listings Crawl.

The worker should expose a fast operator-controlled pause path for live crawling.
The first implementation should not continue crawling blindly after repeated
source-facing failures.

Exact delay and cadence values should be tuned only after terms, robots.txt,
observed source behavior, and the proof-of-concept risk posture are reviewed.

## Source Transports

`NETTIAUTO_SOURCE_TRANSPORT` selects one worker-wide transport:

- `fetch` preserves the normal Bun/Node request path;
- `impit` uses a persistent cookie jar and a coherent Chrome TLS/HTTP profile;
- `flaresolverr` sends requests to the internal browser sidecar and reuses one
  serialized browser session with a bounded TTL.

Compose selects `impit` by default after successful bounded local and production
probes. The transports are explicit choices, not an automatic fallback chain. A
challenge must remain visible to the existing diagnostics and circuit breaker.
FlareSolverr remains an operator-selected diagnostic alternative because it is
materially slower and heavier. The sidecar is pinned to an immutable image,
capped to one CPU and 1 GiB by default, and exposed only on the host loopback
interface.

Run a single probe without writing crawler or listing data:

```bash
bun --cwd apps/worker probe:transport -- \
  --transport impit \
  --url https://www.nettiauto.com/MAKE/MODEL/LISTING_ID
```

For the local FlareSolverr service, replace the transport with `flaresolverr`.
The command prints only bounded status, response shape, byte count, hash,
diagnostics, and v4 parser evidence; it never prints or persists the response
body.

## Failure Handling

Classify failures before retrying:

```text
network_error
redirect_or_sso
blocked_or_challenge
rate_limited
unexpected_content_type
unexpected_body_shape
invalid_ajax_json
parser_schema_error
database_error
```

Network and transient source errors can retry with backoff. Parser schema errors
should preserve the failed raw record or fetch metadata for diagnosis and should
not cause an aggressive retry loop. Block and rate-limit signals should pause
the source query.

## Detail Page Enrichment

The first detail-page enrichment is intentionally narrow: after Search Result
Data discovers a Listing URL, the worker may fetch that detail page with the
same AJAX-style request shape and parse the visible `Päivitetty DD.MM.YYYY`
label into `source_updated_date`. This is a Source-provided update date, not a
created date, sold date, or exact timestamp.

Broader detail enrichment remains a separate lower-priority path that should:

- starts from known `listings`;
- fetches individual listing pages politely;
- stores detail-page Raw Listing Data separately;
- extracts registration number, VIN, equipment, description, and richer
  technical data;
- keeps VIN admin-only.

## Implementation Order

1. Add fixtures for current AJAX JSON, sold AJAX JSON, first-load HTML, and
   JSON-LD.
2. Implement Zod schemas for source payloads and job payloads.
3. Implement parser tests from fixtures.
4. Add Drizzle tables and migration for the database structure.
5. Implement idempotent page persistence against PostgreSQL.
6. Implement a single-page crawl job.
7. Expand to page-range or full Search Query Crawl Runs.
8. Add admin-only crawler status endpoints.
9. Tune cadence and backoff after source constraints are reviewed and the
   proof-of-concept risk posture is explicitly accepted.

## Verification Targets

The first crawler implementation is acceptable when:

- page 1 current and sold AJAX fixtures parse deterministically;
- parser output validates with Zod;
- retrying the same page does not duplicate Listings, Sightings, or Snapshots;
- sold Listings are marked sold only from explicit sold source data;
- a partial crawl is visible as partial, not complete;
- live crawling can be paused or disabled without stopping the web app;
- first-version live crawling is limited to current and sold Search Result Data;
- worker logs identify crawl run, source query, page, parser version, and
  failure class.
